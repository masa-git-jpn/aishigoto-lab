届いた請求書PDFをフォルダに放り込むと、Excelが1つできる。よくある自動化です。

作って、**正解が分かっている請求書150枚**に当てて、1項目ずつ数えました。結果はこうなりました。

| | 想定した書式50枚 | 想定していない書式50枚 | さらに別の書式50枚 |
|---|---|---|---|
| 最初に書いたコード | **50 / 50** | **0 / 50** | 20 / 50 |
| 直したあとのコード | 50 / 50 | 40 / 50 | 30 / 50 |

数字は「請求書番号・発行日・請求元・小計・消費税・合計の6項目と、明細行が全部合っていた請求書の枚数」です。

最初のコードは、想定した書式なら**150枚中の50枚を1つも間違えませんでした。**そして書式が変わった瞬間に**0枚**になりました。

ここまでは、まあ、そうだろうという話です。**問題はその中身でした。**

## 一番怖かったのは、間違いに気づけない10枚

想定外の50枚のうち10枚は、こういう結果でした。

| | 抽出された値 |
|---|---|
| 請求書番号 | 正しい |
| 発行日 | 正しい |
| 請求元 | 正しい |
| 数量・単価・金額 | **全部正しい** |
| 明細合計 = 小計 | **一致する** |
| 品目名 | `当:営業第二部 佐藤 (前月分から` |

正しくは「消耗品一式　※2026年度契約分／担当：営業第二部　佐藤　（前月分からの繰越を含む）」です。

品目名がセルの中で3行に折り返していて、**金額は真ん中の行に印字されていた。**テキストとして読むと、金額の行には名前の真ん中の断片しか載っていません。

金額はすべて正しいので、**合計金額の検算は通ります。**Excelを開いても、金額の列を見ているかぎり何も異常はありません。品目名の列だけが、静かに壊れています。

この10枚は、最初のコードの検算を素通りしました。**「間違っているのに、間違っていないように見える」**のが、この種の自動化で一番高くつく失敗です。

## 何を測ったか

実在の請求書を集めると正解が確定しません。そこで**中身を先に決めてからPDFを作りました。**

15書式 × 各10枚 = 150枚。3つのセットに分けています。

**第1セット（コードを書くときに想定した5書式）**

| | 中身 |
|---|---|
| A | 明細表に格子罫線（HTML→Chromium印刷） |
| B | 横罫線のみ、縦罫線なし |
| C | 罫線なし。レイアウトだけで表になっている |
| D | Excel→PDF変換、格子罫線 |
| E | Excel→PDF変換、全角数字の合計額、値引きの△表記、明細20行 |

**第2セット（コードを書き終えたあとに作った5書式）**

| | 中身 |
|---|---|
| F | 数量・単価の列が無い。見出しも「摘要」だけ |
| G | 品目名がセル内で折り返して複数行になる |
| H | 8%と10%が混在。小計と消費税が2行ずつある |
| I | 紙をスキャンしただけのPDF（文字情報が無い画像） |
| J | 英語ラベル（Invoice No. / Amount）、和暦の日付、¥記号 |

**第3セット（直したあとのコードを書き終えてから作った5書式）**

| | 中身 |
|---|---|
| K | ラベルが「請求No.」「件名」。「合計」の語が無く「ご請求金額」だけ |
| L | 明細の途中に区分ごとの小計行が挟まる |
| M | 列の順番が「金額・単価」と逆。見出しに「(円)」が付く |
| N | 罫線なし。単位の列が空のことがあり、品目に半角スペース入りの型番が混じる |
| O | 明細が2ページに続き、2ページ目には見出し行が無い |

第3セットは**ホールドアウト**です。作ったのはコードを直し終えたあとで、当てるときにコードは1文字も変えていません。「直したつもりのコードが、初見の書式にどれだけ通用するか」を測るためです。

測定の前に、正解の文字がPDFのテキスト層に本当に載っているかを検査しました。スキャン画像の10枚を除く140枚のうち**12枚で、会社名の「西」が見つかりませんでした。**理由は後述します。

## 最初のコード（v1）

やっていることは素朴です。

1. `pdftotext -layout` でテキストにする
2. 「請求書番号」「発行日」などのラベルを目印に正規表現で拾う
3. 明細は「品目〜金額」の見出し行から「小計」の行までを行ごとに解析する
4. 検算する

第1セットでは、6項目すべてと明細389行が**1つも間違いませんでした。**要確認になった請求書も0枚です。

この数字には意味がありません。**そのPDFを見ながら書いたコードだからです。**

## 想定外の50枚に当てる

同じコードを、書式F〜Jの50枚に当てました。修正はしていません。

| 書式 | 明細が完全一致 | 何が起きたか |
|---|---|---|
| F（列が足りない） | 0 / 10 | 明細0行。数量・単価・金額が揃っている行しか認識しない作りだった |
| G（セル内改行） | 0 / 10 | 品目名だけが壊れ、**検算を通過** |
| H（8%と10%混在） | 0 / 10 | 明細0行。税率の列があるだけで行解析が崩れた。小計も10%対象分しか拾えず |
| I（スキャン画像） | 0 / 10 | 全項目が空。エラーは出ない |
| J（英語・和暦） | 0 / 10 | ラベルが違うため請求書番号・日付・金額がすべて取れず |

**50枚中50枚で何かが間違っていました。**

このうち検算が「要確認」として拾ったのは40枚です。残る10枚がGで、前述のとおり静かに壊れていました。

Iのスキャン画像が特に危険です。**文字情報の無いPDFを渡しても、例外は飛びません。**空の結果が返ってくるだけです。「請求額0円の請求書」として集計に混ざります。

## 直した4点

壊れ方を見て、コードを直しました。

**1. テキスト層があるかを最初に確かめる**

```python
def has_text_layer(text, min_chars=40):
    return len(re.sub(r"\s", "", text)) >= min_chars
```

無ければ「OCRが必要」と明示してそのファイルの処理を止めます。0円として通さないためです。

**2. 明細は「表として」取りにいき、駄目ならテキスト行に落とす**

[前回の検証](/lab/pdf-table-extraction-benchmark/)で分かったとおり、格子罫線がある表は表抽出でそのまま取れます。そして**セル内で折り返した文字は、表として取れば1つのセルとしてつながります。**Gが壊れたのは、表を表として扱わずテキスト行として読んでいたからでした。

```python
rows = rows_from_tables(path)   # 罫線がある請求書はこれで取れる
if not rows:
    rows = rows_from_text(text)  # 罫線が無ければテキスト行に落とす
```

**3. 列の数と名前の揺れを許容する**

見出しの語から列の意味を決めるようにしました。「品目／品名／摘要／Description」はどれも品目、「金額／Amount」は金額、というだけの対応表です。数量・単価が無くても、税率の列が増えても動きます。

ひとつ落とし穴がありました。**「単価（Unit Price）」が「単位（Unit）」に化けます。**`unit` を先に判定すると `Unit Price` が単位の列になってしまうので、`price` を先に見る必要がありました。

**4. 小計・消費税が複数行あるときは合算する**

8%と10%で行が分かれている請求書のためです。**この修正は、あとで裏目に出ます。**

## 直したあとの結果

第2セットは 0 / 50 → **40 / 50** になりました。残る10枚はスキャン画像で、これは原理的に読めません。**ただし10枚とも「テキスト層が無い。OCRが必要」と自己申告しています。**

ここで数字を信用しすぎないための注意です。**この40/50は、その50枚を見ながら直したコードの点数です。**実力より高く出ています。

## 初見の50枚（ホールドアウト）

そこで第3セットです。コードを直し終えてから作り、修正なしで当てました。

| 書式 | 明細が完全一致 | 結果 |
|---|---|---|
| K（ラベル違い） | 10 / 10 | 通った |
| L（途中に小計行） | **0 / 10** | 途中の「保守 小計」で明細の読み取りを打ち切り、さらに小計を3つ足して**2倍の額**にした |
| M（列順が逆） | 10 / 10 | 見出しで列を判定しているので通った |
| N（罫線なし・空セル） | 10 / 10 | 通った |
| O（2ページ目に見出しが無い） | **0 / 10** | 2ページ目が表として認識されず、明細が5行で止まった |

**30 / 50。**そして注目すべきはここです。

- 間違えた20枚 → **20枚すべてが「要確認」として自己申告された**
- 検算を通過してしまった誤り → **0枚**

さらに、直した2点がそのまま裏目に出ています。

- **Lの2倍計上**は、「小計を合算する」修正（4点目）が原因です。区分ごとの小計と全体の小計を区別できていません
- **Oの5行で停止**は、「まず表として取る」修正（2点目）が原因です。見出しの無い2ページ目の表を無視しました

参考までに、直す前のコードは同じ第3セットでK（「請求No.」というラベルを読めなかった）・L・Mを落とし、**Oは10/10で通していました。**直したことで、通っていた書式が壊れたわけです。

| | 第1セット | 第2セット | 第3セット | 合計 | 検算を通過した誤り |
|---|---|---|---|---|---|
| v1 | 50 | 0 | 20 | **70 / 150** | 10枚 |
| v2 | 50 | 40 | 30 | **120 / 150** | **0枚** |

## 結論：精度ではなく、気づける仕掛けを設計する

3セット150枚を通して分かったのは、**書式のパターンを潰し切ることはできない**ということです。5つ直したら、次の5つで別の壊れ方をしました。

意味があったのは検算のほうです。v2は30枚を落としましたが、**落とした30枚を1枚残らず自分で申告しました。**人間が目視すべき30枚が名指しで出てくる状態です。120枚は見なくていい。

入れている検算は5つだけです。どれも1行の比較です。

| 検算 | 捕まえたもの |
|---|---|
| 必須項目（番号・日付・請求元・合計）が空でないか | スキャン画像、ラベル違いでの取りこぼし |
| 明細が0行でないか | 列構成の違いによる解析失敗 |
| 明細の金額の合計 = 小計 | Oの途中で止まった明細、Lの二重計上 |
| 小計 + 消費税 = 合計 | Hの税率別集計の取りこぼし |
| 各行の 数量 × 単価 = 金額 | 列のずれ |

この表の3行目と4行目が主力です。**請求書は元々、自分で自分を検算できる形をしている。**その性質を使わない手はありません。

そして重要な限界があります。**この検算はすべて金額の話です。**冒頭のGのように「金額は全部正しく、品目名だけが壊れる」失敗は、金額の検算では原理的に捕まえられません。Gが通るようになったのは検算のおかげではなく、**表として読む経路に変えたから**です。

文字列の正しさは、金額とは別の方法で確かめる必要があります。今回そこまでは作っていません。

## 漢字が「見た目の同じ別の文字」になる件（続き）

[前回](/lab/pdf-table-extraction-benchmark/)、pdfminer系のライブラリが漢字を康熙部首に置き換えることを書きました。今回も出ました。

「西川製作所株式会社」が請求元になっているPDFは（スキャン画像を除いて）14枚あります。そのうち**12枚で、「西」が `⻄`（U+2EC4 CJK RADICAL WEST TWO）になっていました。**

化けた12枚はすべて Chromium の印刷で作ったPDFで、LibreOffice で変換した2枚では起きていません。前回と同じ傾向です。

そして今回分かったことが2つあります。

**1つ目。`unicodedata.normalize("NFKC", s)` では直りません。**

前回対処法として書いた正規化は、康熙部首ブロック（U+2F00〜U+2FD5）には効きます。しかし今回出た `⻄` は**CJK部首補助ブロック（U+2E80〜U+2EF3）**で、こちらにはNFKCの変換規則がありません。素通りします。

配布しているコードでは、部首の名前から対応する漢字を引く表を実行時に組み立てて置き換えています（`_radical_map()`）。ただし完全ではありません。`⻄` の対応先は `襾`(U+897E) であって `西`(U+897F) ではないので、元の字には戻りません。**戻せない前提で、別の方法で読むほうが確実です。**

**2つ目。`pdftotext`（poppler）では同じPDFでも正しく `西` が返ります。**

だからこのスクリプトは、**ヘッダ項目の文字は poppler のテキストから読み、明細の表だけを pdfplumber で読む**という分担にしています。

同じ理由で、記号も置き換わります。`／`（U+FF0F）が `∕`（U+2215 DIVISION SLASH）で返ってきました。見た目は同じで、NFKCでも直りません。**取り込んだ文字列で検索や突合をする予定があるなら、この種の置換は必ず一度確認してください。**

## 使い方

```bash
pip install pdfplumber openpyxl
sudo apt install poppler-utils          # pdftotext

python3 extract_invoices_v2.py ./請求書フォルダ -o invoices.xlsx
```

出力されるExcelは3シートです。

- **一覧**：1行＝1請求書。要確認の行は色が付きます
- **明細**：1行＝明細1行。どのファイルの何行目かが分かります
- **要確認**：検算に引っかかったファイルと、その理由だけ

**運用は「要確認シートに載ったファイルだけ開く」で回ります。**今回の150枚なら、目視は30枚で済みました。

処理時間は**50枚で7〜9秒**でした（Ubuntu 24.04、1回の実行）。100枚でも20秒かかりません。API課金は発生しません。生成AIは1回も呼んでいないからです。

コードは[生データのページ](/data/invoice-benchmark/)に置いてあります。150枚のPDFそのものも入っています。

## この検証で言えないこと

**PDFはすべて自作です。**実在の請求書ではありません。正解を確定させるにはこうするしかありませんでしたが、実際に届く請求書はもっと多様です。**この150枚に無い書式で壊れることは、ほぼ確実に起きます。**そのために検算を入れています。

**「120 / 150」は実力ではありません。**第1セットと第2セットは、コードを書く／直すときに中身を見ています。初見の第3セットの成績は **30 / 50** で、こちらのほうが実態に近い数字です。それでも第3セットの5書式は私が選んだものなので、これも上振れしている可能性があります。

**スキャンPDFは対象外です。**10枚含めましたが、読めません。OCRが必要で、今回はOCRの精度を測っていません。「読めないと分かる」ところまでしか作っていません。

**PDFの作られ方は2通りです。**Chromium の印刷と LibreOffice の変換で作りました。Word、Adobe製品、各社の帳票ツールが作るPDFは内部構造が違うため、同じ挙動になる保証はありません。

**手書きや押印、複数通貨、外税・内税の混在、繰越残高のある請求書は含んでいません。**

**処理時間は各1回の実行です。**桁の話としてだけ読んでください。
