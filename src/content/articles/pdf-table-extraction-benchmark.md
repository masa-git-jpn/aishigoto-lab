「PDFの表をCSVにしたい」という作業は、どの職場にもあります。そして検索すると「pdfplumberが便利」「camelotが強い」といった記事が出てきます。

実際に測ったところ、**どのライブラリを選ぶかは、結果をほとんど決めていませんでした。**決めていたのは、その表に**縦罫線が引いてあるかどうか**でした。

そして、3つのライブラリは条件次第で**表を1つも見つけられず、しかもエラーを出しません**でした。空のリストが返ってくるだけです。

## どう測ったか

実在のPDFを拾ってくると「正解」が分かりません。そこで**中身が確定している表を自分で作り、それをPDFにしました。**

- 日本語の実務的な表を **12種類**（罫線あり／横罫線のみ／罫線なし、結合セル、セル内改行、空セル、9列、52行でページまたぎ、全角数字混在、△のマイナス表記、など）
- それぞれを **2通りの経路でPDF化**
  - **LibreOffice経由**（xlsx → PDF変換）… 日本の実務資料で最も多い作られ方
  - **Chromium経由**（HTML → 印刷でPDF）… 業務システムの帳票出力を模したもの
- 合計 **24本のPDF**

ここで一つ、測定の前に必ずやるべき検査があります。

> **PDFのテキスト層に、正解の全セルの文字が欠けずに載っているか。**

セルの文字が枠からはみ出て切れていたら、それは抽出ライブラリのせいではなくPDFの作りが悪いだけです。24本すべてについて、641セル分の文字が全部PDF内に存在することを確認してから測定に入りました。

抽出したのは次の7つです。

| 方法 | 種類 |
|---|---|
| pdfplumber 0.11.9 | Python / 既定設定 |
| pdfplumber（text戦略） | 同じ。設定だけ変えたもの |
| camelot 1.0.9（lattice） | Python / 罫線ベース |
| camelot 1.0.9（stream） | Python / 文字位置ベース |
| tabula-py 2.10.0 | Java実装のラッパー |
| PyMuPDF 1.28.2 | Python / C実装 |
| pdftotext（poppler 24.02.0）+ 空白で分割 | コマンド1つ。ライブラリを入れない素朴なやり方 |

## 結果：罫線の種類で、ここまで変わる

セル単位の一致率（F1）です。

| 方法 | 格子あり | 横罫線のみ | 罫線なし |
|---|---|---|---|
| pdfplumber | 0.92 | **0.00** | **0.00** |
| pdfplumber（text戦略） | 0.80 | 0.77 | 0.88 |
| camelot（lattice） | 0.92 | **0.00** | **0.00** |
| camelot（stream） | 0.90 | 0.84 | 0.92 |
| tabula-py | 0.79 | 0.37 | 0.94 |
| PyMuPDF | **1.00** | **0.00** | **0.00** |
| pdftotext + 空白で分割 | 0.96 | 0.89 | **1.00** |

**0.00 が並んでいます。**これは「精度が低い」ではありません。**表を1つも検出できなかった**という意味です。

| 方法 | 表を1つも検出できなかったPDFの数 |
|---|---|
| pdfplumber | 8 / 24 |
| camelot（lattice） | 8 / 24 |
| PyMuPDF | 8 / 24 |
| tabula-py | 3 / 24 |
| pdfplumber（text戦略） | 0 / 24 |
| camelot（stream） | 0 / 24 |
| pdftotext + 空白で分割 | 0 / 24 |

落ちた8本は、すべて**縦罫線がないPDF**でした。この3つは**縦横の罫線が交差した格子を探して表を見つける**仕組みなので、縦線がないと表そのものが存在しないと判断します。

問題は、**そのとき例外が飛ばない**ことです。返ってくるのは空のリストです。

```python
tables = page.extract_tables()
# → []
```

自動処理に組み込んでいた場合、**0件を「表がなかった」と解釈してそのまま素通りします。**

そして日本の実務資料で最も多い体裁は、まさに**横罫線だけを引いた表**です。決算資料も、報告書の一覧表も、たいていこの形をしています。

## pdfplumber は、設定を1行変えるだけで直る

これは救いのある話です。pdfplumber の既定は罫線を探す設定ですが、**文字の並びから列を推測する設定**に変えられます。

横罫線だけの表（T03）での実測です。

| 設定 | 表の検出 | セルF1 | 行の完全一致 |
|---|---|---|---|
| 既定 | **0件** | 0.00 | 0 / 9 行 |
| text戦略 | 1件 | **0.94** | **8 / 9 行** |

変えたのはこれだけです。

```python
# 既定（罫線を探す）→ 縦罫線がないと何も返らない
tables = page.extract_tables()

# 文字の並びから列を推測する
tables = page.extract_tables({
    "vertical_strategy": "text",
    "horizontal_strategy": "text",
})
```

ただし万能ではありません。**格子がある表では既定のほうが正確でした**（0.92 → 0.80）。罫線があるならそれを使ったほうが確実です。実務では、**まず既定で試し、0件だったら text 戦略に切り替える**のが妥当な作りになります。

## もう一つの発見：漢字が、見た目の同じ別の文字になっていた

こちらのほうが厄介です。

Chromium経由で作ったPDFを pdfplumber で読むと、こうなりました。

```
抽出結果 : ⽇付   区分   ⼊⾦   出⾦   残⾼
正しくは : 日付   区分   入金   出金   残高
```

**画面上はまったく同じに見えます。**しかし文字コードが違います。

| 抽出された文字 | 正体 | 本来の文字 |
|---|---|---|
| `⽇` U+2F47 | KANGXI RADICAL SUN（康熙部首の「日」） | `日` U+65E5 |
| `⼊` U+2F0A | KANGXI RADICAL ENTER | `入` U+5165 |
| `⾦` U+2FA6 | KANGXI RADICAL GOLD | `金` U+91D1 |
| `⽥` U+2F65 | KANGXI RADICAL FIELD | `田` U+7530 |

康熙部首は、漢字の部首そのものを表すために別に用意された文字です。**部首として存在する漢字（日・月・田・金・入・山・木・大・見・力・比・工など）が、これに置き換わっていました。**

方法ごとの発生数です。同じ24本のPDFに対する結果です。

| 方法 | LibreOffice経由 | Chromium経由 |
|---|---|---|
| pdfplumber | 0 文字 | **50 文字** |
| camelot（lattice） | 0 文字 | **50 文字** |
| camelot（stream） | 0 文字 | **78 文字** |
| tabula-py | 0 文字 | 0 文字 |
| PyMuPDF | 0 文字 | 0 文字 |
| pdftotext + 空白で分割 | 0 文字 | 0 文字 |

**pdfminer を土台にしている pdfplumber と camelot だけで起きています。**PyMuPDF、tabula、pdftotext では1文字も起きませんでした。同じPDFを読んでいます。

実害を具体的に書きます。

- 「田中」が `⽥中` として取り込まれる → **VLOOKUP が一致しない**
- 抽出したCSVを `grep 金額` しても **引っかからない**
- データベースに取り込んで結合すると **その行だけ落ちる**

そして**目視では絶対に気づけません。**文字化けのように「□」になってくれれば分かりますが、正しい字に見えます。

対処は簡単で、取り込んだ直後に正規化を1回かけるだけです。

```python
import unicodedata
s = unicodedata.normalize("NFKC", s)   # ⽥ → 田
```

ただし NFKC は全角英数字も半角に変換します。「１２３」を「123」にしたくない場合は、康熙部首の範囲（U+2F00〜U+2FDF）だけを個別に置き換えてください。

## 意外だったこと：一番素朴な方法が、平均では一番高かった

24本すべての平均です。

| 方法 | セルF1 | 行の完全一致 | 平均処理時間 |
|---|---|---|---|
| **pdftotext + 空白で分割** | **0.949** | **0.755** | **0.016秒** |
| camelot（stream） | 0.884 | 0.541 | 0.143秒 |
| pdfplumber（text戦略） | 0.797 | 0.496 | 0.086秒 |
| tabula-py | 0.699 | 0.429 | 1.193秒 |
| PyMuPDF | 0.667 | 0.667 | 0.067秒 |
| pdfplumber | 0.611 | 0.538 | 0.088秒 |
| camelot（lattice） | 0.611 | 0.538 | 0.801秒 |

`pdftotext -layout` でテキストを出し、2文字以上の空白で列に割るだけ。ライブラリを1つも入れない方法が、平均では最も高く、かつ**最速でした（tabula-py の約75倍速い）**。

ただしこれは**「pdftotextが最も優れている」という意味ではありません。**理由は2つあります。

第一に、この方法は**表を検出しません。**ページ上の全テキストを行として吐き出すだけです。だから「表が見つからない」という失敗が原理的に起きず、平均が押し上がります。表がどこからどこまでかは自分で判断する必要があります。

第二に、**苦手な表でははっきり落ちます。**セル内で改行がある表では 0.72、長い文が折り返される表では 0.61 でした。1つのセルが2行に分かれて、別の行として出てくるためです。

## 実務でどう選べばいいか

この168回の抽出から言えることです。

**1. まず、その表に縦罫線があるかを見る。**
格子がある表なら、どのライブラリでも結果はほぼ同じです。実際、両方が表を検出できた16本のPDFすべてで、pdfplumber と camelot（lattice）の出力は**1文字も違わず完全に一致しました。**選定に悩む意味がありません。速さで選ぶなら PyMuPDF（格子ありでF1 1.00、0.067秒）です。

**2. 縦罫線がないなら、罫線ベースの方法は候補から外す。**
pdfplumber（既定）、camelot（lattice）、PyMuPDF は何も返しません。camelot（stream）か pdfplumber（text戦略）か tabula に切り替えてください。

**3. 「0件だったら別の方法に切り替える」処理を必ず入れる。**
これが最も重要です。0件でもエラーは出ません。次のような形にしておけば、体裁の違う書類が混ざっても止まりません。

```python
tables = page.extract_tables()
if not tables:
    tables = page.extract_tables({
        "vertical_strategy": "text",
        "horizontal_strategy": "text",
    })
```

**4. pdfplumber か camelot を使うなら、取り込み後に必ず正規化する。**
Chromium由来のPDF（Webシステムからの帳票出力）では、漢字が康熙部首に化けます。1行の正規化で防げます。

**5. 抽出したデータは必ず件数で検算する。**
今回の実験は、要するに「正解を用意して突き合わせた」だけです。実務でも、合計金額や件数など**答えが分かっている数字を1つ決めて突き合わせる**のが最も確実な検算になります。

## この検証で言えないこと

**PDFは自作したものです。** 実在の配布PDFではありません。正解を確定させるにはこうするしかありませんでしたが、**スキャンした紙のPDF（画像だけで文字情報がないもの）は対象外です。**それらはどの方法でも0点になり、OCRが必要になります。今回測ったのは「文字情報を持つPDF」に限った話です。

**PDFの作り方は2通りだけです。** LibreOffice と Chromium で作りました。Microsoft Word / Excel、Adobe製品、各種帳票ツールで作られたPDFは内部構造が異なるため、同じ結果になる保証はありません。特に康熙部首の問題は**Chromium由来のPDFでのみ**観測されたもので、他の生成元でも起きるかどうかは分かりません。

**表の種類は12種です。** 縦書き、セルの斜線、複数の表が1ページに並ぶケースなどは含んでいません。

**各1回の実行です。** 処理時間は実行ごとに変動します。桁が違う差（0.016秒 対 1.193秒）は意味がありますが、0.067秒と0.086秒の差は誤差の範囲と考えてください。

**ライブラリのバージョンで挙動は変わります。** 検証日時点のバージョンを検証環境の欄に明記しています。
