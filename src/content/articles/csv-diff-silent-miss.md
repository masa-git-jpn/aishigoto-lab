システムから落とした2つのCSVを突き合わせて、「差分はありませんでした」と報告する。

この作業の怖いところは、<strong>差分が無いのか、差分を見つけられなかったのかが、画面上は同じに見える</strong>ことです。エラーは出ません。0件と表示されるだけです。

そこで、<strong>答えが分かっているCSVを自分で作って</strong>測りました。10,000行の2つのCSVに、実務でよく起きる8種類の差分を種類ごとに仕込み、14通りの突合方法にかけています。判定対象は80,000件です。

数字は<strong>「本当は違う10,000件のうち、違うと言えた件数」</strong>です。多いほど良い。

|---|---|---|---|---|---|---|
| Calc（標準取込）: `=` 比較 | <strong>8,879</strong> | <strong>0</strong> | 10,000 | 6,595 | 10,000 | 10,000 |
| Calc（標準取込）: `EXACT` | <strong>9,501</strong> | <strong>0</strong> | 10,000 | 6,595 | 10,000 | 10,000 |
| Calc（標準取込）: `COUNTIF` | <strong>8,879</strong> | <strong>0</strong> | <strong>0</strong> | 6,595 | 10,000 | 10,000 |

（`VLOOKUP` は1件ごとに全行を線形探索するため全行では終わらず、先頭1,000行で測っています）

<strong>先に断っておくと、どの手法も「同じものを違う」とは一度も言いませんでした。</strong>完全に一致する10,000件を別の列に用意してありますが、14手法すべてで誤検出は0件です。失敗はすべて「見逃す」方向に出ています。<strong>画面には常に「差分は少なめ」と表示される</strong>ということです。

## 先頭ゼロは、10,000件中10,000件が見逃された

いちばん壊れていたのはここです。

商品コードの `0999632506` が、もう片方のシステムでは `999632506` になっている。先頭のゼロが落ちた、よくある状態です。

<strong>CSVをそのまま開いて突合した場合、10,000件すべてが「一致」と判定されました。</strong>`=` でも `EXACT` でも `COUNTIF` でも `VLOOKUP` でも同じです。pandas を `pd.read_csv()` とだけ書いて読んだ場合も、10,000件すべて見逃しています。

理由は単純で、<strong>取り込んだ時点で両方とも `999632506` という数値になっている</strong>からです。比較する前に差が消えています。数式の問題ではないので、どの関数を使っても結果は変わりません。

これは検算しました。仕込んだ10,000件は、数値に変換すると全件がAとBで同じ値になります。つまり数値として読んだ時点で、この差分は原理的に検出できません。

一方、<strong>取り込み時に列を「テキスト」に指定すれば10,000件すべて検出できます。</strong>pandas なら `dtype=str` を付けるだけです。差はそれだけです。

## 16桁の番号：9,007,199,254,740,992 という境界

本題です。16桁の番号の末尾1桁だけを変えた10,000件を突合しました。

| 方法 | 見逃し |
|---|---|
| `=` 比較 | <strong>1,121件</strong> |
| `COUNTIF` | <strong>1,121件</strong> |
| `EXACT` | <strong>499件</strong> |
| `VLOOKUP`+`EXACT` | 54件 / 1,000件 |

見逃した1,121件がどういう番号だったかを調べたところ、<strong>1,121件すべてが 9,007,199,254,740,992 より大きい番号</strong>でした。そして検出できた8,879件は、<strong>8,879件すべてがこの値以下</strong>です。きれいに分かれています。

この数は 2 の 53 乗です。表計算ソフトが数値を格納する形式（倍精度浮動小数点数）が、整数を1きざみで正確に表せる上限がここになります。これを超えると、隣り合う整数が同じ値に丸められます。

実際に、末尾1桁だけ違う2つの番号が、取り込んだ時点で<strong>完全に同じ値になっていた</strong>ものが156件ありました。

```
CSVのA:  9953903775534895
CSVのB:  9953903775534896
取り込み後: どちらも 9953903775534896
```

こうなると、どんな数式を使っても差は出せません。

### 「=」は、値が違っていても「同じ」と答える

ここからが予想していなかった部分です。

完全に同じ値になったのは156件でした。しかし `=` 比較は<strong>1,121件</strong>を「同じ」と判定しています。差の965件は、<strong>格納された値は違うのに「同じ」と答えられた</strong>ことになります。

どれだけ離れれば「違う」と言うのか、基準値から1ずつ離した値を並べて測りました。

| 基準値 | `=` が「違う」と言い始める差 | `EXACT` が「違う」と言い始める差 |
|---|---|---|
| 1234567890123456（2^53よりずっと下） | <strong>1</strong> | 1 |
| 8999999999999998（2^53のすぐ下） | <strong>1</strong> | 1 |
| 9007199254740994（2^53の直後） | <strong>48</strong> | 1 |
| 9999410431301254（16桁の上のほう） | <strong>48</strong> | 1 |
| 99999999999999998（17桁） | <strong>512</strong> | 512 |

2^53 以下では、1違えば1違うと言います。ところが2^53を超えたとたん、<strong>48未満の差は「同じ」</strong>になります。17桁の番号では<strong>512未満の差が「同じ」</strong>です。格納値が実際に2離れていても「同じ」と答えます。

なぜ2^53以下では1違いを検出できるのに、上では大きさに比例した許容差が効くのか。<strong>そこまではこの検証では突き止められませんでした。</strong>分かったのは「境界がどこにあって、どれだけ離れれば気づくか」までです。

### `EXACT` のほうがまだマシだが、安全ではない

`EXACT` は文字列として比較するので、値が丸められても表示が違えば気づきます。それで見逃しが499件まで減っています。

ただし表示にも桁数の上限があります。次の2つは、格納された値は違うのに<strong>表示が同じ</strong>になり、`EXACT` も「同じ」と答えました。

```
CSVのA:  9088500869839780 → 表示 9.08850086983978E+015
CSVのB:  9088500869839782 → 表示 9.08850086983978E+015
```

そして17桁になると `EXACT` も512未満の差を見逃します。<strong>「EXACTを使えば安全」ではありません。</strong>

### 取り込みをテキストにすれば、全部消える

`=` も `EXACT` も `COUNTIF` も `VLOOKUP` も、<strong>列を「テキスト」で取り込めば10,000件すべて検出できました。</strong>見逃しゼロです。

問題は数式ではなく、<strong>数式に届く前に値が壊れていること</strong>でした。

## COUNTIF は大文字と小文字を区別しない

`承認者ID` の列に `EGB204684` と `egb204684` を仕込みました。

`COUNTIF` は、<strong>取り込み条件にかかわらず10,000件すべてを「一致」と判定しました。</strong>`=` と `EXACT` は10,000件すべて検出しています。

`COUNTIF` の照合が大文字小文字を区別しないためです。担当者IDや型番の大小が揺れている表を `COUNTIF` で突合すると、そこは最初から見ていないことになります。

## セル内改行：見逃し3,405件、ただし中身は「無害」寄り

`備考` 列にセル内改行を仕込んだところ、Calc はどの数式でも3,405件を見逃しました。

内訳を機械的に調べたところ、<strong>3,405件すべてが「中身は同じでCRLFとLFの違いだけ」</strong>の行でした。改行を1つ挿入して中身を変えた行（6,595件）は全部検出しています。

つまりこれは、取り込みの時点で改行コードが揃えられたことによる見逃しです。<strong>改行コードの違いを差分と呼びたいかどうかは業務によります。</strong>請求金額の突合なら無害ですし、ファイルの同一性を確かめたいなら見逃しです。`diff` と `comm` はバイト単位で見るので10,000件すべて検出しました。

なお `diff` と `comm` にとってのセル内改行は別の意味で危険でした。10,000行のCSVが、<strong>物理的には13,405行と20,000行のファイルになっています</strong>（正しく引用符で囲まれていても、行単位で読む道具には1レコードが2行に見えます）。今回は全行に差分があったので結果的に全件検出になりましたが、<strong>行がずれた状態で数えた数字</strong>だということは書いておきます。行数が違うファイル同士の `diff` は、どの行とどの行を比べているのかがもう分かりません。

## 正規化してから比較する場合のトレードオフ

空白・全角半角・大文字小文字を揃えてから比較すると、その3種類は<strong>設計どおり検出されなくなります</strong>（全角半角0件、大文字小文字0件、空白は中間の空白が入った2,567件だけ検出）。

これはバグではなく、そういう手法です。表記ゆれの誤検出を減らしたいなら正しい選択で、<strong>16桁番号と先頭ゼロは正規化しても10,000件すべて検出できています</strong>。何を差分と呼ぶかを先に決める、という話です。

## ホールドアウト：集計コードを変えずに、新しいデータへ当てた

ここまでの数字は、集計コードを書きながら見ていたデータのものです。それでは自分に甘い可能性があるので、<strong>集計コードを書き終えたあとで、別スクリプトで新しいデータを作り、コードを1文字も変えずに当てました。</strong>

本番より難しいパターンに差し替えています（17桁・18桁の番号、末尾2桁違い、ゼロ幅スペース、ノーブレークスペース、CRのみの改行、部分的な全角混在）。2,000行です。

| 方法 | 16桁以上の番号 | 先頭ゼロ | 大文字小文字 |
|---|---|---|---|
| Calc（標準取込）: `=` 比較 | <strong>623 / 2,000</strong> | <strong>0 / 2,000</strong> | 2,000 |
| Calc（標準取込）: `EXACT` | <strong>835 / 2,000</strong> | <strong>0 / 2,000</strong> | 2,000 |
| Calc（標準取込）: `COUNTIF` | <strong>623 / 2,000</strong> | <strong>0 / 2,000</strong> | <strong>0 / 2,000</strong> |
| Calc（テキスト取込）: 4手法とも | 2,000 | 2,000 | `COUNTIF`のみ0 |
| Python: 生の文字列比較 | 2,000 | 2,000 | 2,000 |

桁を増やしたぶん、見逃しは大幅に増えました。`=` 比較は<strong>2,000件中1,377件（約69%）を「一致」と判定</strong>しています。

そして見逃した1,377件は、<strong>やはり100%が 2^53 より大きい番号</strong>でした。別のデータでも同じ境界が出ています。誤検出は全手法で0件、対照群（まったく別の値）は全手法で全件検出でした。

## 副実験：文字コードが違うだけの2ファイル

中身が1文字も違わないCSVを、UTF-8 / BOM付きUTF-8 / Shift_JIS の3通りで書き出して突合しました。正解は「差分ゼロ」です。

- <strong>UTF-8 と BOM付きUTF-8</strong>：生の文字列比較で1行が「違う」と出ます。中身はヘッダ行で、先頭の列名が `id` ではなく `﻿id` になっていました。データ500行はすべて一致。pandas は BOM を自動で外すので0件でした
- <strong>UTF-8 と Shift_JIS</strong>：Python も pandas も `UnicodeDecodeError` で読めません。`diff` と `cmp` は「differ」としか言いません

<strong>エラーで止まるぶん、こちらは安全な壊れ方です。</strong>気づかないまま「差分ゼロ」と報告されるより、読めないと言われたほうがいい。

## 副実験：開いて保存し直しただけで、16個中7個の値が書き換わった

最後に、突合とは別の話をひとつ。日付に見える文字列などを16個並べたCSVを、標準設定で開いて、そのまま保存し直しました。

<strong>7個の値がファイルの中で書き換わりました。</strong>

| 元の値 | 保存し直した後 |
|---|---|
| `9999999999999999` | `1E+016` |
| `0012` | `12` |
| `00123456789` | `123456789` |
| `3/4` | `03/04/26` |
| `2026-1-2` | `2026-01-02` |
| `1E5` | `1.00E+05` |
| `(123)` | `-123` |

16桁の番号が `1E+016` になっています。<strong>元の番号はファイルから消えました。</strong>括弧つきの `(123)` が `-123` になるのも、経理の表では困る変換です。

列を「テキスト」で取り込んだ場合は、16個すべてが元のままでした。

ひとつ、<strong>予想が外れた点</strong>も書いておきます。この検証を始める前、私は `1-2` のような値が日付に変換されると予想していました。実際には `1-2` と `2-3` は変換されず、日付になったのは `3/4` のほうでした（`03/04/26` になっています）。日付として解釈される書き方は環境の地域設定に依存します。この環境の日付表示が月/日/年になっている点も含め、<strong>日本語環境のExcelで同じ7個が壊れるとは限りません。</strong>

## 実務でどうすればいいか

80,000件から言えることは3つです。

<strong>1. 番号の列は、取り込むときに「テキスト」を指定する。</strong>
今回、見逃しの原因はすべて取り込み時の型変換でした。テキストで取り込めば、16桁番号も先頭ゼロも見逃しゼロになります。pandas なら `dtype=str`、Calc や Excel の取り込みダイアログなら列を選んで「テキスト」です。<strong>この1手順だけで、この記事の見逃しの大半が消えます。</strong>

<strong>2. 自分の番号が 9,007,199,254,740,992 を超えるか確かめる。</strong>
16桁でも、この値以下なら数値として扱っても1違いを検出できました。超えるかどうかが分かれ目です。17桁・18桁なら確実に危険域です。<strong>桁数ではなく大きさで決まります。</strong>

<strong>3. 突合する前に、正解が分かっている行をわざと混ぜる。</strong>
今回いちばん役に立ったのは、対照群として入れた「まったく別の値」の列でした。これが検出できていれば、少なくとも手法が動いていることは分かります。<strong>逆に言えば、これが無い突合の「差分0件」は、差分が無いことの証明になりません。</strong>

## この検証で言えないこと

数字を出した以上、限界も書いておきます。

<strong>Excel本体では検証していません。</strong> 使ったのは LibreOffice Calc 24.2 です。この環境にExcelが無いためで、記事中の「表計算ソフト」はすべて LibreOffice Calc を指します。倍精度浮動小数点数を使う点は共通なので同じ傾向が出る可能性はありますが、<strong>許容差の48や512という具体的な数字、`COUNTIF` の大文字小文字の扱い、どの値が日付に変換されるかは、Excelで同じとは限りません。</strong>確かめていないので断定しません。

<strong>XLOOKUP は測れませんでした。</strong> この環境の LibreOffice 24.2 に XLOOKUP が無く、`#NAME?` になります。企画時は測る予定でしたが、実行できなかったのでこの記事には数字がありません。

<strong>番号の分布は人工的です。</strong> 16桁の番号を一様乱数で作ったため、10,000件中1,121件が 2^53 を超えました。実務の番号は先頭の桁が決まっていることが多く（クレジットカード番号のように先頭が4や5で始まるなら 2^53 以下です）、<strong>見逃し11.2%という割合そのものは、あなたのデータには当てはまりません。</strong>当てはまるのは「2^53を超えるかどうかで結果が変わる」という構造のほうです。

<strong>「差分」の定義はこちらで決めたものです。</strong> 全角半角の違いや改行コードの違いを差分と呼ぶかは業務によります。この記事では「生の文字列として1バイトでも違えば差分」を正解としました。定義が変われば、正規化してから比較する手法の評価は逆になります。

<strong>取り込み条件は2通りだけです。</strong> 「何も指定しない」と「全列テキスト」の2つで、その中間（一部の列だけテキスト）は測っていません。
