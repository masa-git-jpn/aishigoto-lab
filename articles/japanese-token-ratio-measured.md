日本語のトークン数を見積もるとき、「だいたい1文字1トークン」で計算していないでしょうか。私はそうしていました。

OpenAIの公式ドキュメントには目安が書かれていますが、**英語の話しかありません。**

> 1 token is approximately 4 characters or 0.75 words for English text.
> — [Key concepts | OpenAI API](https://developers.openai.com/api/docs/concepts)

日本語については何も書かれていません。なので測りました。

業務で出てくる文体の日本語文書を16ジャンル・40本（9,676文字）書き下ろし、6つのトークナイザーにかけています。この記事では**測定結果よりも、どう検証したかを厚めに書きます。** 結果だけなら誰でも出せますが、その数字が信用できるかは検証設計で決まるからです。

## 結果（先に要点だけ）

1文字あたりのトークン数です。小さいほど得。

| トークナイザー | 何に使われているか | 日本語 | 英語 |
|---|---|---|---|
| `r50k_base` | GPT-2 / GPT-3 初期 | **1.37** | 0.20 |
| `cl100k_base` | GPT-4 / GPT-3.5-turbo | **0.97** | 0.20 |
| `o200k_base` | GPT-4o / GPT-4.1 / o系 | **0.71** | 0.20 |
| Claude 1〜2 世代 | 当時公開されていたもの | **0.97** | 0.20 |
| Gemma | Googleが公開しているもの | **0.58** | 0.19 |

**「1文字1トークン」がぴたりと当たるのは `cl100k_base` だけでした。** 0.97。GPT-4とGPT-3.5-turboの世代です。

つまりこの目安は**間違って広まったのではなく、一世代前には正しかった。** そして今は違います。現行の `o200k_base` は 0.71 なので、1文字1トークンで見積もると**実際の1.4倍で数えている**ことになります。

同じ日本語の文書が、GPT-3世代と現行世代で**1.91倍**違いました。文章は一字も変えていません。

ここから先が本題です。

## 語彙ファイルが落とせない環境だった

検証環境から `openaipublic.blob.core.windows.net` にも `huggingface.co` にも出られませんでした。`tiktoken` は初回に語彙ファイルをダウンロードする作りなので、これだけで詰みます。

```
NG  o200k_base   ProxyError: HTTPSConnectionPool(host='openaipublic.blob.core.windows.net', port=443)
NG  cl100k_base  ProxyError: ...
```

出られたのは `pypi.org` と `registry.npmjs.org` と `raw.githubusercontent.com` だけ。

ここでミラーから拾ってくることになるのですが、**素性の分からないミラーの語彙ファイルで測った数字には何の意味もありません。** 1バイトでも違えば結果が変わります。

### 公式のチェックサムがパッケージに同梱されている

`tiktoken` の `tiktoken_ext/openai_public.py` を読むと、各語彙ファイルの**SHA-256が定数として書かれています。**

```python
def cl100k_base():
    mergeable_ranks = load_tiktoken_bpe(
        "https://openaipublic.blob.core.windows.net/encodings/cl100k_base.tiktoken",
        expected_hash="223921b76ee99bde995b7ff738513eef100fb51d18c93597a113bcffe865b2a7",
    )
```

つまり**PyPIから入る `tiktoken` 自体が、正解のハッシュを持っている。** ミラーから取ってきたファイルをこれと照合すれば、配布元のファイルとバイト単位で同一であることが保証できます。

写し間違いも防ぎたいので、ハッシュはパッケージから直接読み出して突き合わせました。

```python
def official_hashes_from_package():
    """インストール済みの tiktoken から公式ハッシュを読み出す（写し間違い防止）"""
    import inspect, re
    import tiktoken_ext.openai_public as p
    return set(re.findall(r'hash="([0-9a-f]{64})"', inspect.getsource(p)))
```

結果、4ファイルすべて一致しました。

```
tiktoken パッケージ同梱のハッシュと突き合わせ: OK

OpenAI の語彙ファイル
  OK   cl100k_base.tiktoken  SHA-256 一致
  OK   o200k_base.tiktoken   SHA-256 一致
  OK   p50k_base.tiktoken    SHA-256 一致
  OK   r50k_base.tiktoken    SHA-256 一致
```

ローカルファイルから `tiktoken.Encoding` を組み立てれば、ネットワークに出ずに動きます。`pat_str` と特殊トークンはパッケージの定義に合わせます。

```python
def _load_bpe(path):
    ranks = {}
    with open(path, "rb") as f:
        for line in f:
            if not line.strip():
                continue
            token, rank = line.split()
            ranks[base64.b64decode(token)] = int(rank)
    return ranks

enc = tiktoken.Encoding(name="o200k_base", pat_str=O200K_PAT,
                        mergeable_ranks=_load_bpe("vocab/o200k_base.tiktoken"),
                        special_tokens={ENDOFTEXT: 199999, ENDOFPROMPT: 200018})
```

### Claude 1〜2 世代の語彙は npm に落ちている

現行のClaudeのトークナイザーは公開されていませんが、**Claude 1〜2 世代のものは npm の `@anthropic-ai/tokenizer` に `claude.json` として入っています。**

ただし素直には読めませんでした。`bpe_ranks` は空白区切りのbase64文字列なのですが、

```python
>>> parts = d["bpe_ranks"].split(" ")
>>> parts[:6]
['!', '5', 'IQ==', 'Ig==', 'Iw==', 'JA==']
```

**先頭2要素（`!` と `5`）だけがbase64ではありません。** そのまま全部デコードすると落ちます。

```
binascii.Error: Invalid base64-encoded string
```

読み飛ばせばよさそうですが、**「たぶんヘッダだろう」で進めると測定結果ごと信用できなくなります。** 幸い、同じパッケージにテストが入っていました。

```ts
expect(countTokens('hello world!')).toEqual(3);
expect(countTokens('™')).toEqual(1);
expect(countTokens('ϰ')).toEqual(1);
expect(countTokens('<EOT>')).toEqual(1);
```

先頭2要素を飛ばす実装で、**4件とも再現しました。** これで読み方が正しいと言えます。

もうひとつ、本家の `countTokens()` は符号化の前に **NFKC正規化**をかけています。

```ts
const encoded = tokenizer.encode(text.normalize('NFKC'), 'all');
```

日本語では全角英数が半角に変換されるので、これを省くと数字が変わります。実装に含めました。

## 測り方が壊れていないことをどう示すか

語彙が本物でも、測り方が間違っていれば意味がありません。3つ置きました。

### 1. 対照群に英語を入れる

英語は「1トークンあたり約4文字」という公表された目安があります。ここが大きく外れていたら、測定系そのものを疑うべきです。

結果、全トークナイザーで **0.19〜0.20（1トークンあたり5.05〜5.13文字）** に収まりました。ホールドアウトでも動きませんでした。

ついでに分かったこととして、**公式の目安「約4文字」に対して実測は約5.1文字**でした。今回の英文が事務的で長めの単語を使うためです。**英語ですら3割ずれる。** 目安とはその程度のものだ、という補助線になります。

### 2. 符号化して復号すると元に戻るか

途中で文字が落ちていないかの確認です。全40本で完全一致しました。

```python
bad = [s[:20] for s in samples if tk[name].decode(tk[name].encode(s)) != s]
ok(f"{name} 全{len(samples)}本が完全に復元", not bad)
```

Claude 1〜2 世代だけはNFKC正規化をかけるので、戻り先は正規化後の文字列になります。そこも含めて確認しました。

### 3. ホールドアウト

ここまでの数字は、測定コードを書きながら見ていた文章のものです。それでは自分に甘いので、**コードを書き終えたあとに別ジャンルの文章を新しく8種類書き下ろし、コードを1文字も変えずに当てました。**

求人票・通販の商品説明・社内規程・問い合わせへの回答・健康の説明・研修資料・SNSの投稿・自治体の案内。3,691文字です。

| | 本番 | ホールドアウト | 差 |
|---|---|---|---|
| `r50k_base` | 1.37 | 1.54 | +0.17 |
| `cl100k_base` | 0.97 | 1.08 | +0.11 |
| `o200k_base` | **0.71** | **0.77** | +0.05 |
| Gemma | 0.58 | 0.56 | −0.03 |

順位も傾向も変わりませんでしたが、**数字は1割ほど上振れしました。** 本番には英数字の多いジャンル（APIの説明やファイル名の規則）が入っていて、平均を押し下げていたためです。

つまり **「日本語は1文字あたり◯トークン」という一つの数字は、ジャンル次第で1割は動きます。** 16ジャンル全部での幅は `o200k_base` で **0.54〜0.85**。**16ジャンルすべてで1.0を下回りました。**

なお、コーパスはすべて書き下ろしです。既存の文章を引用していないので全文を公開できます。**偏っていると感じたら、ご自身の文章で測り直せます。**

## 予想と逆だったこと

文字種ごとに切り分けたら、思っていたのと逆の結果が出ました。同じ文字種が続く塊（カタカナ語や漢字熟語）を文章から抜き出して測ったものです。

| 連なり | 字数 | `cl100k` | `o200k` | 例 |
|---|---|---|---|---|
| 漢字 | 1,601 | 1.38 | **0.87** | 専属的合意管轄 / 安全管理措置 |
| ひらがな | 1,846 | 0.82 | **0.62** | じぶんのなまえとばんごうを |
| カタカナ | 645 | 0.92 | **0.61** | セッションタイムアウト |
| 半角英数 | 523 | 0.38 | **0.38** | Authorization / 4901234567890 |

**カタカナは漢字より安い。** 「カタカナ語はトークンを食う」と思っていましたが逆でした。「セッションタイムアウト」のような長いカタカナ語ほど、まとまりで語彙に入っているようです。

一方、**全角英数は高くつきます。** 1文字を単独で符号化したときのコストです。

| | `r50k` | `cl100k` | `o200k` |
|---|---|---|---|
| 半角英数 | 1.00 | 1.00 | 1.00 |
| 全角英数 | **3.00** | **1.84** | **1.55** |

実際の文字列で比べると差がはっきりします。

| | `cl100k` | `o200k` |
|---|---|---|
| `ＡＢＣ１２３` → `ABC123` | **9 → 2** | 5 → 2 |
| `ＳＫＵ－２０２４－Ａ１００` → `SKU-2024-A100` | **15 → 6** | 11 → 6 |

型番や商品コードが全角のまま入った表を貼ると、ここで無駄が出ます。

ただし **Claude 1〜2 世代のトークナイザーは、5例すべてで全角と半角が同数でした。** 前述のNFKC正規化のためです。**この対策が効くかどうかは相手によります。**

## 実務での使い方

- **現行世代なら「日本語の文字数 × 0.7〜0.8」。** GPT-4／GPT-3.5世代なら「× 1.0」。ジャンルで1割動くことは織り込む
- **全角英数は半角に直す。** 表や型番をそのまま貼る前に一手間
- **まれな漢字は高い。** 常用漢字1.06に対して、薔薇・憂鬱・齟齬あたりは1.86（`o200k`）

## この検証で言えないこと

**現行のClaudeとGeminiのトークナイザーは測れていません。** 公開されていないためです。この記事の「Claude 1〜2 世代」は当時公開されていたもので**現行Claudeの数字ではなく**、「Gemma」はGemmaのものであって**Geminiのものではありません。** 同じ会社のモデルでも同じとは限らないので、そのつもりで読んでください。

**コーパスは私の書き下ろしです。** 実在の業務文書ではないので、語彙や言い回しに偏りが残っている可能性はあります。16ジャンルに分けて幅を示したのはそのためです。

**料金には触れていません。** 単価はモデルごとに違いますし変わります。この記事は「同じ文章が何トークンになるか」だけを扱っています。
