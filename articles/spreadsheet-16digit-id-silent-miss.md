2つのCSVを突き合わせて「差分はありませんでした」と報告する作業には、厄介なところがあります。

**差分が無いのか、差分を見つけられなかったのかが、画面上は同じに見える。** エラーは出ません。0件と表示されるだけです。

なので、**正解が分かっているCSVを自分で作って測りました。** 10,000行の2つのCSVに8種類の差分を仕込み、14通りの方法で突合しています。判定対象は80,000件です。

結論から書くと、いちばん危なかったのは16桁の番号ではなく**先頭ゼロ**でしたが、16桁のほうには**きれいな境界**がありました。

## 実験の作り方

### 列ごとに差分の種類を分ける

最初、1つの列にすべての種類の差分を混ぜて入れました。これは失敗でした。

**pandasも表計算ソフトも、型の推定を列単位で行うためです。** 1列の中に数値っぽい値と英字混じりの値が同居していると、列全体が文字列として扱われ、**検証したかった「型変換による取りこぼし」自体が起きません。**

実務のCSVは列ごとに書式が揃っているので、そちらに合わせました。

| 列名 | 仕込んだ差分 | 正解 |
|---|---|---|
| `確認用番号` | なし（常に完全一致） | 同じ |
| `対照用コード` | まったく別の値 | 違う |
| `照合番号` | 16桁番号の末尾1桁違い | 違う |
| `商品コード` | 先頭ゼロの消失（`0999632506` → `999632506`） | 違う |
| `得意先コード` | 前後の空白、全角スペース | 違う |
| `型番` | 半角英数 vs 全角英数 | 違う |
| `承認者ID` | 英字の大文字/小文字 | 違う |
| `備考` | セル内改行、改行コード | 違う |

`確認用番号` 以外は、**生成時に `assert` で「生の文字列として必ず異なる」ことを保証しています。** つまり正解は常に「違う」です。

```python
if category == "same":
    assert va == vb
else:
    assert va != vb, (category, va, vb)
```

### 対照群と、誤検出の測定列

`対照用コード` は**誰の目にも別物**の値を入れてあります。これを検出できない手法は、測定系自体が壊れていると判断できます。今回は14手法すべてが全件検出しました。

`確認用番号` は逆に**常に完全一致**です。ここで「違う」と言ったら誤検出です。**14手法すべてで誤検出0件**でした。つまり**失敗はすべて「見逃す」方向にしか出ていません。**

### セルに値を流し込まず、CSVを実際に開く

ここが重要でした。UNO経由でセルに `setString()` すると、すべて文字列として入ります。それでは**「CSVを開いたときに起きること」を測れません。**

なので CSV インポートフィルタで実際に開いています。取り込み条件は2つ。

```python
STD_OPTIONS  = "44,34,76,1"   # 列書式を指定しない（ダイアログでそのままOK）
TEXT_OPTIONS = "44,34,76,1," + "/".join(f"{i}/2" for i in range(1, 13))  # 全12列をテキスト
```

:::message
列書式は「列番号/書式コード」を `/` でつないで並べます（書式2＝テキスト）。**カンマ区切りにすると黙って無視されます。** 最初これに気づかず、標準取込と同じ結果を「テキスト取込」として1回まるごと測り直しました。
:::

## 結果

数字は「本当は違う10,000件のうち、違うと言えた件数」です。

| 突合の方法 | 16桁の末尾1桁違い | 先頭ゼロの消失 | 大文字小文字 |
|---|---|---|---|
| Calc（標準取込）: `=` 比較 | **8,879** | **0** | 10,000 |
| Calc（標準取込）: `EXACT` | **9,501** | **0** | 10,000 |
| Calc（標準取込）: `COUNTIF` | **8,879** | **0** | **0** |
| Calc（テキスト取込）: `=` / `EXACT` | 10,000 | 10,000 | 10,000 |
| Python: 生の文字列比較 | 10,000 | 10,000 | 10,000 |
| Python: `pd.read_csv()` そのまま | 10,000 | **0** | 10,000 |
| Python: `pd.read_csv(dtype=str)` | 10,000 | 10,000 | 10,000 |
| `diff` / `comm` | 10,000 | 10,000 | 10,000 |

## いちばん壊れていたのは先頭ゼロ

商品コード `0999632506` が、もう片方のシステムでは `999632506` になっている。よくある状態です。

**CSVをそのまま開いて突合した場合、10,000件すべてが「一致」と判定されました。** `=` でも `EXACT` でも `COUNTIF` でも `VLOOKUP` でも同じです。`pd.read_csv()` とだけ書いた場合も10,000件すべて見逃しています。

理由は単純で、**取り込んだ時点で両方とも `999632506` という数値になっている**からです。比較する前に差が消えています。数式の問題ではないので、どの関数を使っても結果は変わりません。

検算もしました。仕込んだ10,000件は、数値に変換すると全件AとBが同じ値になります。**数値として読んだ時点で、この差分は原理的に検出できません。**

## 16桁の番号：9,007,199,254,740,992 という境界

末尾1桁だけを変えた10,000件の見逃しです。

| 方法 | 見逃し |
|---|---|
| `=` 比較 | **1,121件** |
| `COUNTIF` | **1,121件** |
| `EXACT` | **499件** |

見逃した1,121件がどういう番号だったかを調べたら、**1,121件すべてが 9,007,199,254,740,992 より大きい番号**でした。そして検出できた8,879件は、**8,879件すべてがこの値以下**です。きれいに分かれています。

`2^53` です。倍精度浮動小数点数が整数を1きざみで正確に表せる上限がここになります。

実際に、末尾1桁だけ違う2つの番号が、取り込んだ時点で**完全に同じ値になっていた**ものが156件ありました。

```
CSVのA:  9953903775534895
CSVのB:  9953903775534896
取り込み後: どちらも 9953903775534896
```

こうなると、どんな数式を使っても差は出せません。

### 「=」は値が違っていても「同じ」と答える

ここが予想していなかった部分です。

完全に同じ値になったのは156件でした。しかし `=` 比較は**1,121件**を「同じ」と判定しています。差の**965件は、格納された値は違うのに「同じ」と答えられた**ことになります。

どれだけ離れれば「違う」と言うのか、基準値から1ずつ離した値を並べて測りました。

| 基準値 | `=` が「違う」と言い始める差 | `EXACT` が「違う」と言い始める差 |
|---|---|---|
| 1234567890123456（`2^53` よりずっと下） | **1** | 1 |
| 8999999999999998（`2^53` のすぐ下） | **1** | 1 |
| 9007199254740994（`2^53` の直後） | **48** | 1 |
| 9999410431301254（16桁の上のほう） | **48** | 1 |
| 99999999999999998（17桁） | **512** | 512 |

`2^53` 以下では、1違えば1違うと言います。ところが `2^53` を超えたとたん、**48未満の差は「同じ」**になります。17桁では**512未満の差が「同じ」**です。格納値が実際に2離れていても「同じ」と答えます。

48 / 9.0e15 も 512 / 1.0e17 も、およそ 5.3e-15。**大きさに比例した相対的な許容差が効いている**ように見えます。

ただし、**なぜ `2^53` 以下では1違いを検出できるのに、上では許容差が効くのかまでは突き止められませんでした。** 分かったのは「境界がどこにあって、どれだけ離れれば気づくか」までです。

### EXACT のほうがマシだが、安全ではない

`EXACT` は文字列として比較するので、値が丸められても表示が違えば気づきます。それで見逃しが499件まで減っています。

ただし表示にも桁数の上限があります。次の2つは**格納された値は違うのに表示が同じ**になり、`EXACT` も「同じ」と答えました。

```
CSVのA:  9088500869839780 → 表示 9.08850086983978E+015
CSVのB:  9088500869839782 → 表示 9.08850086983978E+015
```

17桁になると `EXACT` も512未満の差を見逃します。**「EXACTを使えば安全」ではありません。**

## pandas は 16桁を取りこぼさなかった

意外だったのがここです。**`pd.read_csv()` をそのまま使っても、16桁の末尾違いは10,000件すべて検出しました。**

digit列は int64 として読まれるためです。int64 は約 9.2e18 まで整数を正確に持てるので、16桁でも17桁でも精度が落ちません。倍精度に落とす表計算ソフトとは事情が違います。

**つまりこれは「浮動小数点の話」であると同時に「表計算ソフト特有の話」でもあります。** 一方で先頭ゼロのほうは pandas も全滅なので、`dtype=str` は結局必要です。

## COUNTIF は大文字と小文字を区別しない

`承認者ID` に `EGB204684` と `egb204684` を入れました。

**`COUNTIF` は取り込み条件にかかわらず10,000件すべてを「一致」と判定しました。** `=` と `EXACT` は10,000件すべて検出しています。担当者IDや型番の大小が揺れている表を `COUNTIF` で突合すると、そこは最初から見ていないことになります。

## ホールドアウト

ここまでの数字は集計コードを書きながら見ていたデータのものなので、**コードを書き終えたあとに別スクリプトで新しいデータを作り、コードを1文字も変えずに当てました。** 17桁・18桁の番号、末尾2桁違い、ゼロ幅スペース、CRのみの改行など、本番に無いパターンに差し替えています。

`=` 比較の検出は **2,000件中623件**まで落ちました。見逃した1,377件は、**やはり100%が `2^53` より大きい番号**です。別のデータでも同じ境界が出ました。誤検出は全手法0件、対照群は全手法で全件検出でした。

## 対策

**取り込むときに列を「テキスト」に指定する。** それだけで、16桁も先頭ゼロも見逃しゼロになります。pandasなら `dtype=str`。

**自分の番号が 9,007,199,254,740,992 を超えるか確かめる。** 16桁でもこの値以下なら数値として扱っても1違いを検出できました。桁数ではなく大きさで決まります。クレジットカード番号のように先頭が4や5で始まるなら `2^53` 以下です。17桁・18桁なら確実に危険域です。

**突合の前に、正解が分かっている行をわざと混ぜる。** 今回いちばん役に立ったのは対照群でした。逆に言えば、**これが無い突合の「差分0件」は、差分が無いことの証明になりません。**

## おまけ：開いて保存し直しただけで、16個中7個の値が書き換わった

日付に見える文字列などを16個並べたCSVを、標準設定で開いてそのまま保存し直しました。

| 元の値 | 保存し直した後 |
|---|---|
| `9999999999999999` | `1E+016` |
| `0012` | `12` |
| `3/4` | `03/04/26` |
| `(123)` | `-123` |

16桁の番号が `1E+016` になっています。**元の番号はファイルから消えました。**

ひとつ**予想が外れた点**も書いておきます。私は `1-2` のような値が日付に変換されると思っていましたが、実際には `1-2` と `2-3` は変換されず、日付になったのは `3/4` のほうでした。**日付として解釈される書き方は地域設定に依存します。**

## この検証で言えないこと

**Excel本体では検証していません。** 使ったのは LibreOffice Calc 24.2 です。検証環境にExcelが無いためで、記事中の「表計算ソフト」はすべて LibreOffice Calc を指します。倍精度を使う点は共通なので同じ傾向が出る可能性はありますが、**48や512という具体的な数字、`COUNTIF` の大小文字の扱い、どの値が日付に変換されるかは、Excelで同じとは限りません。** 確かめていないので断定しません。

**XLOOKUP は測れませんでした。** 環境の LibreOffice 24.2 に無く `#NAME?` になります。企画時は測る予定でしたが、実行できなかったので数字がありません。

**番号の分布は人工的です。** 16桁を一様乱数で作ったため、10,000件中1,121件が `2^53` を超えました。実務の番号は先頭の桁が決まっていることが多いので、**見逃し11.2%という割合そのものは当てはまりません。** 当てはまるのは「`2^53` を超えるかどうかで結果が変わる」という構造のほうです。
